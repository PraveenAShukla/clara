01The problem

One result, two people, and a chance to understand

Abu Dhabi’s premarital screening now includes a genetic test. The result is about both spouses at once, and it is easy to misread.

About two people

Whoever hears it first is left explaining it to the other.

“Carrier” is not “ill”

A carrier is usually healthy. It matters when both carry a change in the same gene.

1 in 4, each pregnancy

A chance, not a diagnosis.

So we set two rules for ourselves: the software never shows one spouse something about the other that they have not agreed to share, and a person, never a model, makes every decision. A model writes words a family reads only in one place, a short, checked and labelled Ask Clara answer. The rest of this page follows one synthetic couple, Noura and Saeed, through the system.

03The rules

One small library decides every step

A folder called core/ decides what may happen next, who may see what, and what is recorded. Same input, same output, no network and no clock, so we can test it on thousands of random cases.

The five phases of a case
The dot follows an at-risk result. Only the specialist can move it from held to released.
Engineering detail · event sourcing, applyOp, result kinds

Clara is a Next.js app. The hosted copy runs on Cloudflare Workers and the same code runs as a Node server in Docker. Nothing in core/ imports from the rest of the app, which also means a hospital system could reuse the rules without our web framework.

A case is a list of events (“lab reported”, “specialist released”, “Noura agreed to share”); the current state is what you get by replaying it, a pattern called event sourcing. History is only ever added to. There is one way in:

An operation that is out of order, repeated, or from a role that may not send it returns the case unchanged rather than throwing, so a retry on bad Wi-Fi does no harm. The server stamps every event with its own time, so timings cannot be back-dated from a device.

A result is one of five kinds: no-shared-change, at-risk-recessive, at-risk-x-linked, needs-specialist (always explained by a genetics professional) and resample. The phases are in core/types.ts (lines 82–87); step in core/machine.ts allows release only from held, only by the specialist, only once a session exists (line 103). Some steps are fixed rules; consent, release and the choice about relatives are people’s decisions. No step is decided by a model.

04Privacy

Each screen is built for one reader

Each role’s view is built from the case one field at a time. For a spouse it is built on the server, so what Noura may not see never reaches her phone at all.

What each device receives
It cycles through the seats on its own; pick one to stop. Struck-through rows are never built into that seat’s view.
autoplay
These are the views each screen shows. In a live room, only the spouse seats receive nothing but their view; staff seats hold the case and build theirs on the device. A spouse’s carrier findings reach the other spouse only if they choose to share them (partnerCarrier, carrierShared in PartnerView). Gene names appear only in the specialist’s panes, which are not shown here. For an X-linked result the result is the woman’s own: she sees it first, with a line on her own health and a metabolic referral, and decides when, or whether, her partner learns it; until then he sees a neutral line. The property test in tests/core/view.test.ts builds 2,000 random cases and fails if any view holds a field its role may not see.

A private check-in, and questions for the session. After reading their own explanation, each spouse can privately mark “I feel overwhelmed” or that they are still unsure what a carrier is, and pick the questions they want covered in the session. Only the specialist sees these marks and questions; each phone holds only its own. Property tests in tests/core/view.test.ts check that the other spouse’s phone, the family doctor’s view and the lab’s view are byte-identical whether or not a spouse does this. Try it on the spouse app.

Engineering detail · where views are built, staff seats

The functions are partnerView, doctorView, labView and specialistView in core/view.ts. A field the role may not see is never copied into the view; it is not hidden with CSS.

Staff seats work differently in the prototype. In a live room the specialist, family doctor and lab seats receive the case and build their view on the device (shownTo in lib/room/room-core.ts). Their screens show only their own view, but the data is on the device. That is acceptable for synthetic cases; a real deployment would build staff views on the server and add clinician sign-in, which the prototype does not have.

05The record

Who saw what, without storing what

Every time information about a spouse moves, the record adds an entry holding a fingerprint (SHA-256 hash) of what moved, never the content. Each entry also holds the previous entry’s fingerprint, so any edit breaks the chain.

Editing the record
On a loop: change one character in entry 2, then try to cover it up by re-sealing entry 2. Press any button to take over.
autoplay
Hashes are shortened to 12 characters for display. In tests/core/audit.test.ts the same check runs on 2,000 random one-byte edits, and every one is caught.
Engineering detail · appendAudit, canonical JSON
export function appendAudit(ledger: AuditEntry[], drafts: AuditDraft[], ts: string): AuditEntry[] {
  let out = ledger
  for (const d of drafts) {
    const prev = out.at(-1)
    out = [...out, sealed({ ...d, seq: (prev?.seq ?? 0) + 1, ts, prevHash: prev?.hash ?? GENESIS })]
  }
  return out
}

core/audit.ts, lines 35–42; verifyChain below it recomputes every hash

Hashes are taken over canonical JSON (keys sorted), so equal data always gives an equal hash. Because the record holds fingerprints only, a spouse can withdraw consent, the content is deleted, and the record still verifies. Each phone builds “who has seen what about you” from the entries about that spouse alone.

Engineering detail · Durable Object, host key, sync, limits

On the hosted site every room lives inside one Cloudflare Durable Object, a single small server with its own storage, reached by name (getByName("rooms")). Inside it runs the same room handlers as the Node server. Each room is also written to the object’s SQLite-backed storage under room:<code> and read back if Cloudflare clears the object’s memory. A second object, Reviews, holds only the team’s usability check. Rooms are deleted after 3 hours idle or 12 hours at most.

/** The seat's signature: 64 bits of an HMAC over the room and the seat, keyed by the room's host key. */
export const seatMac = (hostKey: string, code: string, id: string) =>
  bytesToHex(hmac(sha256, utf8ToBytes(hostKey), utf8ToBytes(`${code}/${id}`))).slice(0, 16)

lib/room/seats.ts, lines 30–32

When a room is made, the server creates a random 24-character host key and returns it to the device that made the room, which keeps it in local storage, signs one token per seat for the QR codes, and can end the room. A phone only ever receives its own seat’s token. Verification compares all 16 characters without stopping early, so timing leaks nothing. Cutting the signature to 64 bits seems reasonable to us for a room that lasts at most 12 hours, but it is one thing an outside security review should check.

Staff screens apply their own pending operations at once, replaying them over the last confirmed state with the same applyOp the server runs, and drop them if the room refuses. Operations travel in numbered batches of at most 12:

// A retried batch (its reply was lost) is answered again, not applied twice.
if (batch <= (entry.lastBatch.get(client) ?? -1))
  return { version: entry.state.version, results: ops.map(() => "noop"), ...shownTo(entry.state, seat, ids) }

lib/room/registry.ts, lines 110–112; retry timing in lib/room/room-transport.ts

Updates arrive as Server-Sent Events with a version number. A device that sees a gap fetches a fresh copy with ?since=, falls back to polling if the stream drops, and refreshes when the page returns to the foreground. Room codes are six characters from a 31-symbol alphabet without 0, O, 1, I or L (about 887 million codes). Limits, in lib/room/protocol.ts: 100 rooms, 200 events per room, 12 operations per request, 16 devices per room and 256 in all, 8 KB per request on the Node server.

07The front door

One Worker in front of everything

On the hosted site, Next.js exports every page as static files and a small hand-written Cloudflare Worker routes the rest.

Where a request goes

Engineering detail · two builds, logging, access code

pnpm cf:build sets CLARA_STATIC=1 and Next.js writes static files to out/; wrangler.jsonc runs the Worker first. Without the flag Next builds a standalone Node server, which the Docker image runs (node server.js) with rooms held in memory. Cloudflare’s request logging and metrics are off (observability.enabled: false, send_metrics: false). The team pages’ access code arrives as ?k=, is swapped for a cookie holding a keyed hash of it, and is stripped from the address; those pages are also marked not to be indexed. The rate limit keeps one visitor from flooding the model; it is a courtesy, not a security boundary. Each caller’s pace lives in its own Durable Object, keyed by a daily keyed hash of the address, so it holds across restarts; a pace that cannot be read lets the call through, and a daily count that cannot be read answers by rules, so a fault never passes the 2,000-call daily cap. Every API route has a body cap, refused with 413 before the body is parsed (/api/ai 64 KB, room operations 8 KB; lib/body-limit.ts). The self-hosted container enforces the same access gate when CLARA_GATE=1 is set, and uses PUBLIC_ORIGIN as its address for the UAE PASS return (deploy/CONTAINER.md).

08Words

Every fixed sentence a family reads is written by people, to be signed by clinicians

1,071 fixed sentences, each in English and formal Arabic, versioned and hashed: 954 that families read in the app (including the feminine forms used when the specialist is a woman) and 117 study texts. A model never writes one of these; the only model-written words a family can see are Ask Clara’s short, checked answers, labelled as such. Today all 1,071 are drafts awaiting a clinician and an Emirati Arabic reviewer, and Ask Clara labels each one “Clara’s fixed answer, a draft not yet signed by a clinician”, not “approved”. Family-facing screens say “Clara’s fixed answer”, never “approved”; only staff sign-off labels, where a reviewer really approves, say approved.

Engineering detail · signing, Arabic design

Each sentence (“atom”) records whether it is a draft or signed, and the hash of the exact signed text, so an edit after signing shows up. Arabic was designed alongside English: IBM Plex Sans Arabic next to IBM Plex Sans, Markazi Text for headings, its own spacing and a right-to-left layout. Every chance is written in words and drawn as a picture.

09Care

From understanding to an appointment

Lawful options shown unranked and shuffled, a referral that carries only what the receiver needs, and every step time-stamped.

A referral, tracked to the end
sentreceivedacceptedbookedattendedclosed
In pregnancy the referral is marked urgent, and the programme checks whether the couple is seen within 48 hours of the clinic knowing.

A doctor-ready summary, one per reader. The summary page opens on a finished synthetic case: the family doctor’s pre-test brief, then the session summary. The clinician’s copy holds the finding and what to go over again. Each spouse’s copy holds only what their own phone shows, in their language and at their own reading choice (full text, short lines or pictures first).

Engineering detail · FHIR, shuffle, relatives

The referral is a valid FHIR R4 ServiceRequest (core/fhir.ts). All five kinds pass a public FHIR server’s own validator with no errors, and are stored, read back unchanged and deleted (eval/fhir/roundtrip.run.ts; shown on Evidence). It goes through Malaffi; that connection is a prototype stand-in today because Malaffi has no public test environment. What it carries: no gene, no answers, nothing about relatives, and each spouse consents to what is sent. Options are shuffled per spouse with a fixed seed (core/order.ts), so no option is always first and the order shown can be reconstructed. Declining is a full option; questions about cost, cover or faith go to a person. The specialist’s console shows the pathway clock: result, session booked, session held, referral sent, appointment.

Clara never names or stores a relative. Each spouse chooses for their own side: tell no one, pass on a letter, or ask a counsellor to make contact, which needs a completed comprehension check and a 72-hour cooling-off. For relatives the couple share, the stricter choice wins.

Written answers, the meaning check and every other task, text a family types included, go to K2 first and to OpenAI (gpt-6.1-terra, United States) only when K2 does not answer, is too slow or sends an unreadable reply (tests/lib/fallback.test.ts). The lab report reaches the model without names or sample codes, and the session brief holds no names. K2’s public API is reached through Amazon Web Services in Singapore (checked by DNS on 18 Nov 2026), so neither model is UAE-hosted; the UAE’s ICT Health Law (Federal Law No. 2 of 2019, Art. 13) limits health data leaving the country, and Clara marks that clause, and DoH Responsible AI 3.1.4.5.1, a gap until both run on UAE-hosted models, before any real family. The Ask screen links to the privacy page, which says so. The API response carries the model’s name in an x-clara-model header; MODEL_OFF=1 turns AI off for everyone.

The care agent’s seven tools (read report, route, draft brief, release, offer time, draft referral, follow up) are ordered and limited in code (lib/ai/agent.ts); anything leaving the clinic waits for the specialist, and release is refused by policy every time. In Rehearsal, the same verifier blocks numbers not on the fact sheet, directive phrasing, termination wording and named relatives.

13Privacy in numbers

Noise that hides any one couple

Publish a count, publish it again after one couple joins, and the difference is that couple. So programme figures get calibrated random noise: differential privacy, merged on 15 November, audited on 18 November and now covered by 45 release tests and 5 key-store tests.

Releasing one count many times
The true count is 37. Values keep dropping on their own; each is the true count plus the Laplace noise Clara uses.

This is a sketch of the mechanism, not of the product’s screen. In Clara the noise is drawn once per cohort and kept, so reloading the page cannot be used to average it away, and rounding and clamping happen after the noise, which costs no extra privacy.
Engineering detail · the maths, medians, limits

Counts get discrete Laplace noise (integer in, integer out), calibrated like a Laplace of scale b = 10 / ln 20 ≈ 3.34, so 95% of the noise is within ±10 (P(|noise| > 10) ≈ 4.3%). The unit of privacy is one couple joining or leaving the cohort; δ = 0. Formally, any output becomes at most eε times more or less likely; smaller ε is stronger privacy.

privacy cost ε = Δ · ln 20 / 10 (Δ = the most one couple can change the figure) budget costs add up within a release; at ε = 5 every later figure is withheld

Medians use the exponential mechanism, picking a value from a 6-hour grid up to four weeks, favouring values near the true median; they are withheld below 100 cases. Groups under 10 are withheld outright. Noise is drawn once per cohort from a 256-bit key of crypto randomness (an 18 November audit replaced a 32-bit seed that could be brute-forced in minutes), and each share’s small-cell rule uses its own denominator (core/release.ts, eval/dp/AUDIT.md).

Limits: the small-group rule is a common health-statistics rule, outside the formal guarantee. ε is per release; nothing enforces a lifetime budget across releases yet. In the prototype the noise key lives in the browser. And the equity gap needs every group’s shares, so in every synthetic cohort we tried, up to 540 couples, the budget ran out first and the gap was withheld; the page says so rather than show it.
